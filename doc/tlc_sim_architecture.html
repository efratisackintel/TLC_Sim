Architecture decisions — what to be aware of

The modeling choices behind this simulator. They make it a faithful teaching model — not a bit-exact firmware port. Know these before drawing conclusions from a run.

DecisionAssumption / implication
Intel PER model = TLC PER modelUses Intel's measured EHT PER‑vs‑SNR curves as the TLC's link model, assuming the AP's PER behaviour is similar (roughly symmetric link). A real peer/AP may have different curves.
SISO scored with the 1×2 PER modelSingle‑stream (SISO) TX is evaluated with the 1×2 curve, assuming the AP uses MRC receive combining with at least 2 antennas (2‑antenna RX diversity). MIMO uses the 2×2 curve.
Canonical curve subsetCurves are the full‑band (SU), PPM 0, RU‑index 1, AWGN, LDPC operating point. Puncturing, other RUs, and non‑AWGN / real‑interference profiles are not modelled.
AWGN‑only channel (no multipath, no CFO)The PER model is AWGN only — verified across the full .fig set (78 figs / 25,536 curves, all Channel = AWGN) — with no carrier‑frequency offset (PPM = 0). No channel‑D, no TGn/TGac multipath, nothing else. Consequence: on the raw AWGN curves there is no delay spread, so a longer GI only adds cyclic‑prefix overhead with no robustness benefit → GI 0.8µs would always win. Channel length is therefore added on top by a synthetic GI‑vs‑delay‑spread ISI penalty (see the next row and B2), which makes GI selection meaningful.
Delay‑spread / GI penalty is a synthetic modelBecause the curves are AWGN, channel length is added by a synthetic (NOT empirical) inter‑symbol‑interference model, not measured data. A channel profile carries an RMS delay spread τ (small room 0.5µs, office 1µs, outdoor 3µs). When τ ≤ GI the guard covers the echoes → no effect (pure AWGN). When τ > GI, the tail leaks into the next symbol → an SNR penalty and an irreducible PER floor, both growing with the excess ratio τ/GI − 1. This makes GI selection meaningful (longer GI survives longer delay spread) but the numbers are illustrative knobs, not calibrated to real channel measurements. See B2 for the exact model.
PER curves = 4000‑byte packetsThe measured PER curves were captured at a fixed 4000‑byte packet (PSDU). Real traffic uses varying sizes, so PER (and thus SR) must be adapted to the actual packet length — a shorter packet has lower PER at the same SNR, a longer one higher (PER scales roughly with bit count). Not yet applied here.
Success‑Ratio driven, not SNRThe TLC decides on measured Success Ratio (like the firmware). SNR is used only to synthesise SR from the PER curve because there is no real radio; RSSI would be a fallback only.
Retry table (airtime fallback)A failed primary transmission is redelivered at a fallback rate, so throughput dips to ~the fallback rate, not to zero. Built like the firmware (_rsMngBuildRatesTbl): entry 0 = the sent rate (the test rate during a probe), and the fallback ladder is taken from the stable column — during a search cycle the retry table is still active and its fallbacks are the pre-search committed rate, not the test column (for dwell/upscale the base is the primary). Modeled as an airtime-weighted delivery: effective tpt = delivered bits ÷ total airtime (failed attempt + successful retry). The rate decision still uses the primary rate's SR (which stays low), so a too-high rate is still abandoned — only the throughput depth is corrected. In the Simulation tab the achieved line turns red while the retry table is backfilling. Approximation: per-rung mean (no per-MPDU BA bitmap, no explicit SIFS/BA/backoff overhead).
PSD penalty is band-dependentSelected by the Band control: 2.4 GHz = total-power limited → full −10·log₁₀(BW/20) penalty; 5 GHz = hybrid → penalty only above 80 MHz (−10·log₁₀(BW/80)); 6 GHz = PSD-limited → no penalty (wider BW is free up to the total cap). See §9 · TX power. Still a proxy for the real SAR/TAS/PA/EIRP caps (table-driven, not a formula).

MIMO & guard‑interval penalty fitted from the log
mimo= / lgi=		Why: the AWGN curves assume an ideal 2×2 channel and give the 3.2 µs (4×LTF) curves ~1 dB advantage at low SNR, so the sim preferred MIMO / 3.2 µs where the real FW stayed on SISO M1 0.8 µs (ZoharBadLog: real MIMO M0 = 81% where AWGN says 100%; real M2 at 1.6 µs = 45% where the 3.2 µs curve says 94%). What: an extra SNR loss (dB) is subtracted for MIMO (mimo=) and for 1.6/3.2 µs GI (lgi=), fitted per trace from first‑transmission success ratios after the SISO short‑GI SNR fit (ZoharBadLog: mimo=2, lgi=0.5; fit error 14% → 2%). Caveat: scenario‑specific corrections, not universal constants; 1.6 µs probes are scored on the 3.2 µs curves (no 1.6 µs data).
Longer retry time per failed attempt
MC_FAIL_S = 10 ms		Why: the sim recovered from a failed A‑MPDU too fast (~0.2 ms per failed MPDU vs ~0.9 ms in the real log), so its 400‑failure counter filled ~4× faster → too many search cycles (37 vs 27) and blocked cycles (14 vs 4). The real FW pays a BA timeout, doubled backoff, RTS and retries through the table after every un‑ACKed A‑MPDU. What: in Monte‑Carlo dwell windows, each A‑MPDU with no ACK at all adds 10 ms of airtime (Python: emulator.FAIL_S). Caveat: a fitted value (swept 0–50 ms; 10 ms best matched the trap length and blocked‑cycle count), not derived from timing specs; it lowers throughput only when whole A‑MPDUs are lost.
Throughput modelThe per-rate expected throughput is taken verbatim from the firmware table expectedTptHe in fw/src/umac/main/dataPath/rateScaleMng/rateScaleMng.c — the exact same table the real RS_MNG uses to compare columns. The simulator embeds the full firmware table indexed by bandwidth × GI (0.8/3.2µs) × NSS (SISO/MIMO) × MCS 0–13 (stored as Mbps×10; e.g. 80 MHz/SISO/0.8µs/MCS13 = 604 Mbps), so it is not a linear BASE_TPT × BW × NSS × GI extrapolation. Note these are the firmware's expected (effective) values — already below the nominal PHY rate (e.g. ~5765 Mbps nominal for 320/MIMO/0.8µs vs the firmware's effective figure) — and aggregation / AMSDU / SIFS / BA / airtime overheads are still not modelled, whereas the real RS_MNG maximises airtime-aggregated throughput.
Column climb via getBestRateOn a column/BW switch the search picks the lowest MCS whose throughput beats the stable column (mirrors firmware _rsMngGetBestRate). The full column graph / next‑columns table is simplified to ±1 BW · NSS · GI neighbours.
Rate grid & scopeMCS 0–13, GI 0.8 / 3.2 µs, collision as an independent loss factor. TPC, DCM, ER, STBC and legacy‑column nuances are out of scope.
Not bit‑exactA teaching / limit model of RS_MNG, not a line‑for‑line port of rateScaleMng.c.
RSSI ↔ SNR link budget (with an 8 dB margin)Converting SNR to RSSI (dual chart axis, lab alignment, and the XLSX RSSI to SNR sheet) uses NoiseFloor = −174 + 10·log10(BW) + NF + Margin with Intel noise figure ≈ 4 dB (firmware SIM_GROUND_MARGIN in usimLibLmacTlc.c) plus an ~8 dB RSSI implementation margin so the calculated RSSI matches the driver's RSSI→MCS mapping (SAS). That 8 dB is a derived guardband (RX implementation loss + front-end/antenna noise beyond the 4 dB modem NF + fading/operating margin), not an explicitly documented constant — the source is the RSSI to MCS Mapping SAS.docm breakpoints, where the margin is implicit.

How the TLC (RS_MNG) works — full flow

The real firmware rate controller is the Rate-Scale Manager (RS_MNG / TLC), per-station in UMAC, and it is Success-Ratio driven (not SNR). Below: the whole closed loop, the search cycle, the timers, and the statistics — with what this simulator models vs. simplifies. fw/src/umac/main/dataPath/rateScaleMng/

1 · The closed loop — UMAC decides, LMAC executes
  • UMAC · RS_MNG chooses the rate and builds the Link-Quality command (lqCmd->rate_scale_table): primary rate + fallbacks.
  • ↓ LQ_CMD pushed down to LMAC / uCode
  • LMAC / HW transmits, walks the retry chain per frame, counts txed / acked per rate.
  • ↑ statistics returned to UMAC
  • RS_MNG feeds the stats into the state machine → may rebuild the table (scale / search / column switch) → new LQ_CMD.

3 · Search cycle — step by step
  • Trigger — one of four start reasons (table 4).
  • Pick candidate columns from the column graph (up to MAX_COLUMN_CHECKS = 4 of MAX_NEXT_COLUMNS = 8).
  • For each candidate, _rsMngGetBestRate() picks the lowest MCS whose expected tpt beats the current column — not the incumbent's MCS.
  • Run a short test window (UPSCALE_AGG_FRAME_COUNT = 20 frames) at the candidate; measure SR × tpt.
  • SWITCH_TO_TEST_COL if it wins, else REVERT_TO_STABLE_COL.
  • Fallback = last known-good rate: the revert target and the incumbent score are the last MCS that met the 90% hold threshold — never a rate that just failed a probe. On a PER cliff (e.g. MCS7 100% → MCS8 0%) this stops the search from “settling” back onto the dead MCS8.
  • Telemetry: SEARCH_CYCLE_START/END, TRY_COLUMN_SWITCH, SCALE_ACTION.

What does "SR < 90%" measure over? The success ratio is computed per statistics window counted in frames — 2000 in the stable state, 20 in a probe/test — not over a fixed time. A window closes when its frame counter fills, so its wall-clock length depends on the traffic rate (~10–20 ms on a saturated link, hundreds of ms at realistic offered load). The 90% / 95% thresholds act on an IIR-filtered (EWMA) SR across those windows, not a single one. A dwell that starts failing (SR below the 15% force-down threshold) is aborted within a short reaction window rather than running the full 2000 frames — so a wrong rate commitment can't waste a whole optimal window (~300 ms at 20 MHz), and the search always falls back to the last known-good rate, never one that just failed.

It's a first-order IIR low-pass filter (Infinite Impulse Response) — the same thing statistics calls an EWMA (exponentially-weighted moving average). One recursion: s = α·new + (1−α)·s_prev (here α ≈ 0.4: ~40% newest window, 60% history; a single pole at 1−α = 0.6). It reacts quickly to a real change yet smooths single-window noise, so one unlucky window can't flip the decision — it "remembers" the last ~2 windows with exponentially fading weight, using just one multiply-add and one state variable.

5 · Rate scaling & the upscale probe
  • Downscale — free & immediate: the lower fallback rates already have stats from retries, so it drops when SR is insufficient or a lower rate has higher tpt.
  • Upscale — needs a probe: the higher rate isn't in the table, so RS_MNG makes it the test rate (top of the table, 20-frame window) and sets tryingRateUpscale.
  • Good probe → next action is STAY → the higher rate becomes the PR (table rebuilt around it). Bad probe → downscale back.
  • Throttled by UPSCALE_MAX_FREQUENCY; a higher MCS that just failed is ignored for UPSCALE_IGNORE_HIGHER_MCS = 1000 ms. No throttle inside a search cycle.
  • Fast-fail dwell: an optimal (2000-frame) window whose SR collapses below the 15% force-down threshold is aborted after a short (~20-frame) reaction — not held for the whole window. The FW reacts within a few BlockAck stat updates, so a wrongly-committed rate can't waste a full optimal window (~300 ms at 20 MHz).
  • Recovery / stale stats: stats older than RS_MNG_TIME_STAT_RESET_THRESHOLD are reset (not blended with the old ~0 SR), and a power/RSSI change kicks a fresh search — so when a fade lifts, the TLC re-probes with a clean slate instead of crawling up through stale success ratios.
6 · Retry table — the fallback ladder (built by UMAC, run by LMAC)
  • Primary rate ×N (initial entries)
  • ↓ lower MCS in the same column
  • ↓ bandwidth reduced to 20 MHz
  • ↓ MIMO → SISO, single antenna (+ antenna toggle)
  • ↓ legacy / non-HT rates, down to the lowest

9 · What this simulator models vs simplifies
  • Models: SR-driven decisions, RSSI/SNR warm start, expected-tpt column climb (getBestRate), gated upscale + ignore-failed-MCS cooldown + stale-stat reset, last-known-good fallback + fast-fail dwell, search triggers (success count/time, fail), STAY vs SEARCH, PER from measured curves.
  • Simplifies: upscale is a gated step, not a real 20-frame test window; no offered-load clock (saturated link → compressed SC timing); retry table not executed (primary-rate SR only); no aggregation / AMSDU / TPC; column set = ±1 BW · NSS · GI, not the full 22-column graph.

TX power — regulatory limits & the PSD penalty

IEEE 802.11 doesn't set power limits — it defines the spectral mask, EVM (which forces per-MCS backoff: 4096-QAM / MCS13 needs several dB less power than MCS7), and TPC. The real limits are regulatory, and come as two caps: a total EIRP cap (dBm) and a spectral-density (PSD) cap (dBm/MHz). The device transmits at EIRP = min(total_EIRP_cap, PSD_limit + 10·log₁₀(BW_MHz)) — so whether a wider channel costs per-tone SNR is band-dependent.

Per-tone power vs bandwidth — by band

Flat green = no PSD penalty (6 GHz, wider BW is free per tone). Grey dashed = fixed-total-power reference (−3 dB per BW doubling) — what the sim's PSD penalty assumes; the purple gap at 320 MHz is the −12 dB it applies. 2.4 GHz (only 20/40) tracks the fixed-power slope; 5 GHz (only up to 160) stays flat until its EIRP cap binds. × marks the valid channel widths.

6 GHz power classes (PSD-defined)
  • LPI (Low-Power Indoor): PSD ≈ 5 dBm/MHz, total cap 30 dBm → 20 MHz = 18 dBm … 320 MHz = 30 dBm (cap). Per-tone constant across the whole range.
  • VLP (Very-Low-Power): low PSD / ~14 dBm total, no AFC.
  • Standard Power: with AFC, higher PSD (~23 dBm/MHz).
What the firmware actually applies
  • PPMCS calibration tables — per-MCS · per-BW · per-chain power, incl. the EVM / linearity backoff (high QAM ⇒ less power).
  • PSD limits — first-class: phyEngineSetAuxPsdPowerLimit(), host DynamicPsdLimit, regulatory source arbiter (dBm/MHz, per domain / band).
  • SAR (g_sarDb) and TAS (time-averaged SAR) caps · TLC backoff (tlcBackoff → _swTxpPowerLimitCalc).
  • Applied ≈ min(PPMCS, regulatory·PSD, SAR, TAS) − backoff — table + regulation driven, not a formula.
Effect on this simulator
  • The PSD penalty is realistic in the total-power / SAR-capped regime (2.4 GHz, or any band once it hits the total cap).
  • It is too pessimistic for PSD-limited 6 GHz (LPI/SP below the cap), where wider BW is ~free per tone — which is why it's a toggle.

Search cycle over time — the periodic behavior

Yes — the simulation mimics this loop. During DWELL the emulator (LMAC surrogate) transmits with the chosen primary rate + retry table over long 2000-frame windows. The TLC steps out into a SEARCH cycle using the real firmware trigger (_rsMngShouldStartSearchCycle): failures (>400 frames) start a search immediately; successes (>4500 frames) start one only if >300 ms since the last search (bypassed right after a fail cycle, to re-probe upward fast). It then tries neighbouring columns/rates, picks the best PR + table, and returns to DWELL.

When does a SEARCH cycle start? — the condition, made simple

While in DWELL the TLC just counts frames. Two counters fill up: failed frames and succeeded frames. Whichever counter fills first decides if and when we step out to search.

Left = things going wrong. Too many failures ⇒ drop out immediately (no timer) to find a rate that survives. Right = things going well. Lots of successes ⇒ we could try a faster rate, but a time-gate (>300 ms) stops us searching too often — unless the previous cycle failed, in which case we re-probe up straight away. That mix of reactive failures + rate-limited successes is why search cycles look bursty during fades and evenly spaced (~300 ms) on a steady link.
