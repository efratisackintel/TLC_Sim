⚙️ How the simulation works behind the scenes

The whole thing is one closed loop running on a virtual clock. Nothing happens simultaneously — it's strictly sequential, single-threaded. It's not frame-by-frame: each pass processes a whole window of frames at once, then jumps the clock forward by that window's airtime. That's what makes it fast.

while ( t < total_ms )loop until the scenario's virtual time is used up
1 · Channel — ground truth at time t
channel.state(t) → SNR, collision, delay-spread
2 · Emulator — transmit a whole window
simulate_window(): acked = round(N × (1 − PER)) — one calc for N frames
3 · TLC — the rate picker decides
tlc.on_stats(stats, t) → new rate table + next window size (search vs dwell)
4 · Log + advance clock
dt_ms = window × airtime, then t += dt_ms — jump forward by the window
⟲ loop back to step 1 with the new time t and the TLC's new rate table

🔁 One calc per window — not once, not per frame

Each turn of the loop does exactly one simulate_window() call (one PER lookup + one multiply). So the number of calcs = the number of windows the scenario is chopped into. There are two window types:

Window typeSizeCalcsWhen
Dwell (STAY)DWELL = 2000 frames1 calcSteady state — emitted back-to-back while the link holds.
Search cycleSEARCH = 20 frames per candidateN calcs (one per neighbour tried)Periodically, once ~SUCCESS_LIMIT frames pass and the ~300 ms search guard clears.

📏 Example — a steady scenario (5000, 32 = 5 s at SNR 32 dB)

The channel never changes, but the sim is not a single calc, and not one calc per search cycle either. Here's a real slice of the timeline — 2 dwell windows and 2 search cycles — read it left to right, top to bottom:

① Dwell window — 2000 frames · 1 calc
TLC is happy on its current rate (state STAY). We transmit 2000 frames in one shot: acked = round(2000 × (1 − PER)). Success ratio is high, so the rate is held. It counts these 2000 successes toward the search trigger.
clock: t = 0 → ~400 ms  (dt = 2000 × airtime)
② Dwell window — 2000 frames · 1 calc
Same story, another 2000-frame calc. But now the running success counter has crossed SUCCESS_LIMIT and the ~300 ms search guard has elapsed → TLC decides: "link looks great, let me test if an even faster rate works." It arms a search cycle.
clock: ~400 → ~800 ms
③ Search cycle #1 — 3 candidates × 20 frames · 3 calcs
TLC builds a short list of neighbour rates (e.g. higher MCS / wider BW). Each candidate gets a tiny 20-frame probe = one calc each. It scores their throughput, keeps the best, then settles back to STAY on the winner. Because probes are only 20 frames, this whole cycle costs almost no airtime (~a few ms).
clock: ~800 → ~805 ms  (3 × 20 frames)
…back to dwell windows for a while…
The winning rate is now held with 2000-frame dwell calcs again, until the success counter + guard timer trip the next search.
④ Search cycle #2 — 3 candidates × 20 frames · 3 calcs
Same as ③, just later in time. Since SNR is steady at 32 dB, the search usually re-confirms the same rate (no better neighbour) and settles right back — a cheap "is anything better yet?" check that repeats periodically for the whole scenario.
clock: (some hundreds of ms later)

So across the full 5 s: mostly dwell calcs (one big 2000-frame window each, ~400 ms of virtual time) with short search cycles (3 tiny calcs each) sprinkled in — on the order of ~15–30 calcs total, not thousands of per-frame simulations. That's the speed.

🏎️ Why it's so fast

📦

Windows, not frames

A 2000-frame window collapses into a single multiply: N × (1 − PER). No per-frame loop (unless Monte-Carlo mode is on).

📖

PER from a lookup table

Frame-error rate is read from measured LUTs (per_lut.js), not computed from physics at run time.

⏱️

Virtual clock

Time t only exists as a number that jumps by dt_ms. No real waiting — thousands of ms simulate instantly.

🧠 Simultaneous or tick-by-tick?

QuestionAnswer
Is anything simultaneous?No. One sequential loop, single-threaded.
Tick after tick?Not per frame — it steps window by window (tens–thousands of frames per step).
What drives it forward?A virtual clock t that jumps by each window's airtime dt_ms.

⚙️ How to set up a scenario

A “scenario” is just a list of channel conditions over time. You describe how good/bad the link is, second by second, and the simulation plays the firmware’s rate picker through it. Here is the whole recipe:

  1. Pick your radio settings first (Live decision tab). The scenario reuses the Band, Max BW, Antennas and PSD/power chosen on the 🎛 Live decision tab. Set those to the device you want to model, then come back here.
  2. Choose a preset or write your own. Use the preset buttons for common shapes (a steady level, a slow fade, a cliff…), or type lines yourself in the big text box.
  3. Write one line per segment. Each line is one stretch of time with its channel quality. Format:
    ms, SNR[, SNR_end[, collision[, profile]]]
  4. Run it. Press ▶ Run scenario. The charts on the right show what rate TLC chose, the throughput it got, and how it compares to the best possible (“genie”).
  5. (Optional) compare with a real lab log. Load a reference JSON to overlay measured hardware results and check the model against reality.

📝 What each field on a line means

FieldRequired?What it does
msYesHow long this segment lasts, in milliseconds. e.g. 1000 = 1 second.
SNRYesChannel quality in dB — higher = cleaner signal = faster rates. Low SNR forces TLC down to slow, robust rates.
SNR_endOptionalGive a second value to make the SNR ramp smoothly from SNR to SNR_end across the segment (simulates walking away / fading).
collisionOptionalFraction 0–1 of airtime lost to other traffic/interference. 0.2 = 20% of frames collide.
profileOptionalThe multipath environment: awgn, small room, office, outdoor (or a delay-spread τ in µs). Omit to use the Live tab’s Channel profile.
obss<bw>=POptional, anywhere after SNRBursty interference on the wider channels only: each A-MPDU sent at ≥ <bw> MHz is wiped with probability P (e.g. an OBSS on the upper 160 MHz → obss320=0.8). Losses are whole-A-MPDU, so a short 20-frame test can pass by luck when Monte-Carlo is on.
Rule of thumb: you only ever need the first two fields (ms, SNR). Add the extras only when you want to model a fade (SNR_end), a busy channel (collision), or a specific room type (profile).

💡 What is this simulation, in plain words?

Your WiFi chip constantly has to answer one question: “how fast can I send data right now without it getting lost?” Send too fast and frames fail and have to be resent (slower overall). Send too slow and you waste a good connection. The firmware component that makes this call is the TLC — the rate picker. This page lets you watch it think.

Think of driving a car. The SNR is how clear the road is. When the road is clear (high SNR) you can floor it (fast rate). When it gets foggy (low SNR) you slow down so you don’t crash (frames don’t get lost). TLC is the driver constantly adjusting speed to conditions — and this simulation is a dashcam replay of that driving.

🎯 What the simulation actually does

🌦️

You set the weather

You describe the channel over time (the SNR line, plus optional collisions & room type). That’s the “road conditions”.

🧠

TLC decides

The real firmware logic (ported faithfully) picks a rate: how many bits per symbol (MCS), channel width, antennas, guard interval.

📊

You see the result

Charts show the chosen rate, the throughput achieved, and the “genie” — the best a perfect oracle could have done.

🧩 The words you’ll see, decoded

TermIn plain words
SNR (dB)How clean the signal is. Big number = clear line, small number = noisy/weak.
Rate / MCSHow much data is packed into each transmission. Higher = faster but needs a cleaner channel.
Success RatioThe share of frames that arrive OK. TLC’s real goal: keep the fastest rate that still gets frames through.
SEARCHTLC “test-driving” a nearby faster setting to see if the channel improved. If it wins, it switches; if not, it reverts.
GenieAn imaginary perfect picker that always knows the ideal rate. It’s the score to beat — TLC can’t see the future, the genie can.
Retry tablePlan B, C, D… if a frame fails, it’s resent at a slower, safer rate so the data still gets there.
Why it matters: a good rate picker means your video call doesn’t freeze and your download stays fast even as you move around. This tool lets engineers see and test that decision-making without needing real hardware and a lab.
